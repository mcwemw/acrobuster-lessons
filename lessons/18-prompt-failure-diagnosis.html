提示失效不是玄學：五個可診斷的失效模式，同一個根因Prompt Failures Aren't Random: Five Diagnosable Failure Modes, One Root Cause

「換個詞再試試看」不是診斷——那是在猜。五種提示失效（敏感性、幻覺、諂媚、過度拒絕、偏見）每一種都有可辨識的指紋、一個可重現的測試、和一個第一步修法；而這五種失效的根源其實是同一件事：next-token 預測。先識別你碰到的是哪一種，才有辦法工程化地修它。

"Try different wording until it works" isn't a diagnosis — it's a guess. Each of the five prompt failure modes (sensitivity, hallucination, sycophancy, over-refusal, bias) has an identifiable fingerprint, a reproducible test, and a first fix; and all five trace back to the same root: next-token prediction. Name the failure mode first — then you can engineer the fix.

是什麼 · What it is

Week 6 講義的核心主張（Slide 18）：「提示為什麼失效——以及為什麼那些失效不是隨機的。」Slide 19 給出答案：

「幻覺不是 bug。諂媚不是人格缺陷。敏感性不是怪癖。它們都是同一個底層機制的後果。」

那個底層機制是 next-token 預測（卡 05）——模型在猜「最可能的下一個字」，所以它天生就會：

  • 在不同問法下給出不一致的答案（敏感性）
  • 用流暢的假話填空（幻覺）
  • 選讓你開心的答案而不是對的（諂媚）
  • 把灰色地帶當危險訊號擋掉（過度拒絕）
  • 把訓練語料的歷史偏見帶進輸出（偏見）

Slide 22 說：每種失效都能說清楚它的指紋、成因、測試法、第一步修法。以下是那張診斷表：

其中幻覺有一個讓工程師最切身的具體案例：package hallucination。Spracklen et al.（arXiv:2406.10279，USENIX Security 2025）對 576,000 個 prompt、16 個模型測試：商業模型有 5.2%、開源模型有 21.7% 的回覆包含不存在的套件名稱，研究者偵測到逾 20 萬個捏造套件名，並把相應的攻擊手法命名為 slopsquatting——惡意行為者已把與這些假名完全相同的套件上傳到 npm / PyPI，等工程師跑 npm install 中招。幻覺在你的答案裡只是不準確；在 code generation 裡它成為供應鏈攻擊向量。

這條攻擊鏈分三步，每一步單看都合理，合起來就是災難：

  1. ① AI 幻覺產生假套件名。開發者叫 AI 編碼助理（Copilot / Claude / Cursor）寫 code，AI 發明並推薦一個在 npm / PyPI 上根本不存在的函式庫或依賴（例如 aws-helper-sdk）。
  2. ② 攻擊者預先搶注。攻擊者分析、追蹤「AI 常幻覺出哪些套件名」，把那些名字原封不動註冊到公開 registry，底下塞惡意 payload（後門、竊密程式）。
  3. ③ 誤裝。開發者或自動化 agent 信任 AI 的推薦，直接跑 npm install … / pip install …，把攻擊者的惡意程式下載進專案。

注意第三步的「自動化 agent」分支：若是 agent 無人攔截地跑安裝，整條鏈就全自動走完——這正是 卡 04「評估軌跡、收回控制」為什麼不是空話。這個攻擊面的完整治理（vs typosquatting、詞源、三層防線）見 卡 20。

The attack chain has three steps, each individually reasonable, catastrophic together: ① AI hallucinates a package name — a developer asks an AI coding assistant (Copilot / Claude / Cursor) for code, and it invents and recommends a library that doesn't exist on npm or PyPI (e.g. aws-helper-sdk); ② attackers pre-register it — they track which names AI models commonly hallucinate and register those exact names on public registries with a malicious payload (backdoor, data stealer); ③ inadvertent installation — trusting the AI, the developer or an automated agent runs npm install / pip install and pulls the attacker's malware straight into the project. Note the "automated agent" branch of step 3: with no human to intercept, the whole chain completes unattended — which is exactly why card 04's "evaluate the trajectory, take back control" is not a platitude.

Week 6 opens with a thesis (Slide 18): "Why prompts fail — and why those failures are not random." Slide 19 delivers the answer: "Hallucination is not a bug. Sycophancy is not a personality flaw. Sensitivity is not a quirk. They are all consequences of the same underlying process" — that process being next-token prediction (see card 05). Slide 22 makes the engineering contract explicit: for each failure mode we can state what it looks like, why it happens, a test, and a first fix. The five-row triage table above is that contract.

The package hallucination finding (Spracklen et al., USENIX Security 2025, arXiv:2406.10279) puts a dollar figure on what "hallucination as engineering risk" means: across 576k prompts and 16 models, 5.2% of commercial and 21.7% of open-source responses contained fabricated package names; over 200,000 unique fake names were observed; malicious actors have already registered matching packages on npm and PyPI to catch developers who pip install whatever the LLM suggests. The researchers named the attack surface slopsquatting.

為什麼重要 · Why it matters

Slide 22 說得直接：「'try different wording until it works' is not a diagnosis。」換詞再試是在玄學，不是在做工程。工程做法是：先識別你碰到的是哪一種失效，再對症下藥——就像你不能靠猜 commit message 修 test failure，你要先看 stack trace。

這讓 卡 03「意圖—輸出落差」和卡 14「先有評測才調 prompt」進化成可操作的流程（作者觀點 Author's view）：

  1. 重現失效——寫一個能穩定觸發問題的 test case（若你無法重現，就無從診斷）
  2. 識別類別——用上面五種失效的指紋比對，確定是哪種
  3. 對症測試——用該失效對應的測試法確認（paraphrase / pushback / demographic swap …）
  4. 第一步修法——非「試換詞」，而是特定工具：檢索接地、指令模板、voting、角色分離、Context 擴充

Sclar et al.（arXiv:2310.11324，ICLR 2024）對敏感性給了一個讓人驚訝的量化：同一個任務、只改格式——小到加不加句號——就能讓準確率相差 76 個百分點。這告訴你：你以為「prompt 設計好了」，但只要換個微小的詞序，模型就已在玩完全不同的遊戲。Paraphrase test 不是謹慎，是最低度的健全性檢查。

一句話帶走 · Takeaway

「換個詞再試試」不是軟體工程——先用 paraphrase / pushback / demographic swap 識別你碰到的是哪一種失效，再對症下藥；幻覺最惡的一種已經有名字了：slopsquatting，不存在的套件被人佔名了。

"Try different wording" is not software engineering — first use paraphrase / pushback / demographic-swap tests to name which failure mode you're dealing with, then apply the matching fix. The worst form of hallucination already has a name: slopsquatting, and the fake packages have already been claimed.
